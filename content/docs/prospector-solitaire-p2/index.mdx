### Настройка проекта для этой главы [!toc]
Вместо того чтобы следовать стандартной процедуре настройки
проекта, вам нужно будет продолжить работу над проектом из
предыдущей главы. Для этого у вас есть два варианта:
    - Вы можете продолжить работу в папке проекта из предыдущей главы.
    - Вы можете создать дубликат папки проекта из предыдущей главы.
Иногда - особенно если вы работаете с этой книгой в рамках курса и
вам нужно сдавать работы по двум главам отдельно - может быть
полезно держать проекты этих двух глав отдельно.  

Если вы хотите создать отдельную вторую папку проекта для этой
главы, следуйте этим инструкциям:  

1. Убедитесь, что вы закрыли Unity перед созданием дубликата
любой папки проекта.
2. Найдите папку проекта из предыдущей главы на жестком диске
(с помощью Проводника Windows или Finder в macOS).
3. macOS: щелкните правой кнопкой мыши по папке и выберите
«Дублировать». Дубликат папки появится в том же окне Finder.
Windows: Щелкните правой кнопкой мыши по папке и выберите
«Копировать». Затем щелкните правой кнопкой мыши на фоне
того же окна Проводника и выберите «Вставить».
4. Щелкните правой кнопкой мыши по новой папке и выберите
«Переименовать». Переименуйте новую папку в «Prospector
Part 2».
5. Откройте Unity Hub и нажмите кнопку «Открыть» вверху.
Перейдите к папке с новым проектом и откройте ее.
6. Чтобы избежать путаницы в дальнейшем, вам следует
изменить название проекта. Откройте окно «Настройки
проекта» (*Edit > Project Settings*) и перейдите на вкладку «Player» в левой части
окна. Затем измените «Product Name» на «Prospector Part 2».
7. Если вы используете какую-либо систему управления версиями
или исходным кодом (например, Unity Plastic SCM), вам
необходимо отсоединить этот проект от системы управления
исходным кодом предыдущей главы. Видео, демонстрирующее,
как это сделать, можно найти в главе 32 на сайте книги по
адресу http://book.prototools.net.
</Callout>

как он рассчитывается.  

### Управление раундами Prospector [!toc]
Сначала нужно сделать так, чтобы игра знала, когда она закончилась. Это
нужно проверять только один раз после каждого нажатия игроком на
карту, поэтому проверка будет вызываться в конце
`Prospector.CARD_CLICKED()`.    

1. Откройте скрипт Prospector в Visual Studio и добавьте новые методы
`CheckForGameOver()` и `GameOver()` между
`SetMineFaceUps()` и статическим методом `CARD_CLICKED()`,
показанным в листинге кода, а также между единственной строкой в конце `CARD_CLICKED()`.  

        Листинг кода Prospector.cs

```c#
public class Prospector : MonoBehaviour {
    …

    public void SetMineFaceUps() { … }


    /// <summary>
    /// Test whether the game is over
    /// </summary>
    void CheckForGameOver() { // a
        // If the mine is empty, the game is over
        if ( mine.Count == 0 ) {
            GameOver( true ); // Call GameOver() with a win
            return;
        }

        // If there are still cards in the mine & draw pile, the game’s not over
        if ( drawPile.Count > 0 ) return;

        // Check for remaining valid plays
        foreach ( CardProspector cp in mine ) {
            // If there is a valid play, the game’s not over
            if ( target.AdjacentTo( cp ) ) return;
        }

        // Since there are no valid plays, the game is over GameOver( false ); // Call GameOver with a loss
    }

    /// <summary>
    /// Called when the game is over. Simple for now, but expandable
    /// </summary>
    /// <param name="won">true if the player won</param>
    void GameOver( bool won ) {
        if ( won ) {
            Debug.Log( "Game Over. You won! :)" );
        } else {
            Debug.Log( "Game Over. You Lost. :(" );
        }

        // Reset the CardSpritesSO singleton to null
        CardSpritesSO.RESET(); // b
        // Reload the scene, resetting the game
        // Note that there are TWO underscores at the beginning of "__Prospector…
        SceneManager.LoadScene( "__Prospector_Scene_0" );
    }


    /// <summary>
    /// Handler for any time a card in the game is clicked
    /// </summary>
    /// <param name="cp">The CardProspector that was clicked</param>
    static public void CARD_CLICKED(CardProspector cp) {
        // The reaction is determined by the state of the clicked card
        switch (cp.state) {
        …
            case eCardState.mine:
        …
            break;
        }

        S.CheckForGameOver(); // This is now the last line of CARD_CLICKED() // c
    }
}
```
- a. Вставьте новые методы `CheckForGameOver()` и `GameOver()`
между существующим методом `SetMineFaceUps()` и
статическим методом `CARD_CLICKED()`. Я предпочитаю
размещать статические методы в конце скриптов.
- b. Статические поля, такие как CardSpritesSO.S, не
сбрасываются при перезагрузке сцены. Эта сохранность позволит
нам переносить счет из одного раунда в следующий, но также
требует от нас осторожности при сбросе некоторых статических
полей перед перезагрузкой сцены. Каждый раз при загрузке или
перезагрузке сцены `CardSpritesSO.INIT_STATICS()`
пытается установить синглтон CardSpritesSO.S. Если бы этой
строки здесь не было, CardSpritesSO.S не был бы нулевым при
перезагрузке сцены, и была бы сгенерирована ошибка.
- c. Буква S. перед `CARD_CLICKED()` необходима, поскольку
`CARD_CLICKED()` - это статический метод, которому нужно
вызвать нестатический метод `CheckForGameOver()`, поэтому ему
требуется ссылка на экземпляр класса-синглатона S.

2. Сохраните все скрипты в Visual Studio и вернитесь в Unity, чтобы
протестировать игру.  

Теперь в игру можно играть и повторять ее, и она знает, когда выиграла
или проиграла. Чтобы проверить проигрыш, запустите игру, щелкните по
стопке раздачи, пока она не опустеет, а затем выполняйте любые
доступные вам ходы до тех пор, пока не останется ходов. После этого сцена должна отправить
сообщение `«Game Over. You Lost. :(»` в консоль и перезагрузиться, после чего начнется
новый раунд. Чтобы проверить, работает ли победа в игре, может
потребоваться несколько попыток.

### Совет [!toc]
ВСЕГДА СТАРАЙТЕСЬ НАЙТИ ЭФФЕКТИВНЫЕ СПОСОБЫ ТЕСТИРОВАНИЯ
РАЗЛИЧНЫЕ УСЛОВИЯ ИГРЫ В качестве примера того, как
этого делать не стоит, я часто видел, как студенты проходят весь
уровень игры, чтобы протестировать сражение с боссом в конце
уровня, вносят небольшую поправку в некоторые настройки, а
затем снова проходят весь уровень, чтобы повторно
протестировать сражение с боссом.  

Пожалуйста, помните, что ваше время - ваш самый ценный
ресурс, и действуйте соответственно. В этом примере студентам
следовало бы создать отдельную тестовую сцену, содержащую
только сражение с боссом, чтобы провести все свои настройки, а
затем - только после завершения настроек - протестировать босса в контексте более крупного уровня.

В качестве примера правильного подхода: когда Дженова Чен и
команда thatgamecompany разрабатывали свою последнюю игру
Sky, они включали в каждую тестовую сборку скрытое меню,
которое позволяло им загружать одно из множества мест на
любом уровне игры и настраивать своего игрока с помощью
любых способностей, одежды и т. д., которые игрок в конечном
итоге мог бы найти в игре. Таким образом, они могли легко
протестировать любую ситуацию во всей игре с помощью
(правда, нескольких) пунктов меню.  

Еще один пример правильного подхода - тестирование боевых
ошибок в игре Skyrates, над которой работала моя команда в
аспирантуре. Время от времени игроки сталкивались с
странными ошибками в бою, которых мы никогда не видели. Я
дал возможность любому игроку экспортировать зашифрованный
файл CombatData, содержащий все конфигурационные данные
для боя, и отправить его нам по электронной почте.  

Используя эти файлы CombatData, мы смогли воссоздать и
устранить некоторые крайне редкие ошибки, с которыми мы
никогда бы не столкнулись в ходе тестирования, которое наша
небольшая команда могла провести самостоятельно.  

Создавая свои игры, всегда думайте о том, как сделать
тестирование проще и быстрее. Реализация способов,
позволяющих вашей команде загружать любую ситуацию в игре и способы,
позволяющие игрокам легко сообщать о редких ошибках, займет
немного времени на начальном этапе, но всегда окупится позже.  

В случае с короткой игрой, такой как Prospector, вам не нужно
делать ничего подобного, например, специально тасовать карты
так, чтобы выиграть было всегда возможно, но полезно подумать
о самом коротком способе тестирования побед и поражений
(например, как можно быстрее опустошить колоду розыгрыша,
чтобы проверить поражение), и вам всегда следует помнить о
быстром тестировании на протяжении всего процесса разработки
игры.
