## Метафора объектной ориентации

Проще всего описать объектную ориентацию с помощью метафоры. Представьте себе стаю
птиц. Стая может состоять из сотен или даже тысяч отдельных птиц, каждая из которых должна
обходить препятствия и других птиц, при этом не отставая от стаи.
Стаи птиц демонстрируют блестяще скоординированное поведение, которое долгие годы не
поддавалось моделированию.

### Моделирование стаи птиц монолитным способом

До появления объектно-ориентированного программирования (ООП) программа представляла
собой, по сути, одну большую функцию, которая делала всё. Эта единственная функция
управляла всеми данными, перемещала спрайты на экране и обрабатывала всё — от ввода с
клавиатуры до игровой логики, музыки и графики. Такая попытка сделать всё с помощью одной
гигантской функции теперь называется монолитным программированием.  

>Конечно, это резкое упрощение многолетней истории программирования, но оно помогает донести суть.  

Чтобы смоделировать стаю птиц монолитным способом, было бы логично сохранить большой
массив птиц и создать программу, которая бы учитывала каждую птицу в стае и пыталась бы
сгенерировать для них поведение, характерное для роя. Такая программа по отдельности
перемещала бы каждую птицу из положения в одном кадре в положение в следующем, а также
хранила бы все данные о птицах в массиве.  

Такая монолитная программа была бы очень большой, громоздкой и сложной для отладки.
Например, если бы классы Enemy и EnemyZig из предыдущей главы были объединены в
один монолитный класс, управляющий всеми врагами, код выглядел бы так, как показано в
листинге далее.  

Листинг (Не вводите этот класс в Unity.)

```c#
using System.Collections;
using System.Collections.Generic;
using UnityEngine;

public class MonolithicEnemyController : MonoBehaviour {
    // The List of all enemies. This is populated in the Unity inspector
    public List<GameObject> enemies; // a
    public float speed = 10f;

    void Update () {
        Vector3 tempPos;

        foreach ( GameObject enemy in enemies ) { // b
        tempPos = enemy.transform.position;

        switch ( enemy.tag ) { // c
            case "EnemyGO":
                tempPos.y -= speed * Time.deltaTime;
                break;
            case "EnemyZigGO":
                tempPos.x = 4 * Mathf.Sin(Time.time * Mathf.PI*2);
                tempPos.y -= speed * Time.deltaTime;
                break;
        }

        enemy.transform.position = tempPos;
        }
    }
}
```

a. Этот список GameObjects содержит всех врагов. В данном примере ни к одному из
GameObjects-врагов не привязан код.  

b. Этот цикл `foreach` проходит по каждому GameObject в списке enemies.  

c. Поскольку у врагов нет собственного кода, для хранения всей информации о всех видах
движения, доступных врагам, требуется использование оператора `switch`. Обратите
внимание, что для работы этого кода также необходимо, чтобы каждый GameObject был
помечен тегом «EnemyGO» или «EnemyZigGO».  

>Я обычно избегаю использования тегов, но поскольку этот пример кода касается именно того типа программирования,
которого я рекомендую вам избегать, я решил, что в данном случае теги вполне подойдут.  

В этом простом примере код довольно короткий и не очень «монолитный», но ему не хватает
элегантности и расширяемости кода из главы «Классы». Если бы кто-то создавал игру с 20
различными типами врагов, используя этот монолитный подход, единственная функция
`Update()` легко разрослась бы до нескольких сотен строк по мере добавления вариантов для
каждого типа. К счастью, есть лучший способ. Добавление 20 дополнительных врагов с помощью
метода объектно-ориентированного подклассирования привело бы к созданию 20
небольших подклассов (таких как EnemyZig), каждый из которых был бы коротким и простым
как для понимания, так и для отладки.  

Когда ООП пытается смоделировать стаю птиц, вместо одной монолитной функции ООП
использует другой подход, моделируя каждую отдельную птицу, ее восприятие и действия (все
локально для самой птицы).

### Моделирование стаи птиц с помощью ООП и боидов

До 1987 года было предпринято несколько попыток смоделировать поведение птиц в стае и
поведение рыб в косяке с помощью методов монолитного программирования. Обычно
считалось, что для генерации сложного скоординированного поведения стаи одной функции
необходимо управлять всеми данными в симуляции.  

Это предубеждение было развеяно с публикацией статьи «Стаи, стада и косяки:
распределенная поведенческая модель» (Flocks, Herds, and Schools: A Distributed Behavioral
Model) Крейга У. Рейнольдса в журнале «Компьютерная графика» в 1987 году. В этой
статье Рейнольдс описал невероятно простой объектно-ориентированный подход к
моделированию поведения, похожего на поведение роя, который он назвал «боидами» (Boids).
На самом базовом уровне «боиды» используют всего три простых правила:  

- Предотвращение столкновений: избегайте столкновений с соседями по стае
- Согласование скорости: попытка согласовать скорость с ближайшими товарищами по стае
- Центрирование в стае: попытка оставаться рядом со средним положением соседей по стае
