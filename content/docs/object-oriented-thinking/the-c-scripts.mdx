- **Boid**: вы прикрепите этот скрипт к префабу Boid, и его задача - управлять движением
каждого отдельного Boid. Поскольку это объектно-ориентированная программа, каждый
Boid будет думать самостоятельно и реагировать в соответствии со своим собственным
пониманием мира.
- **Neighborhood**: этот скрипт также будет прикреплен к префабу Boid и отслеживает, какие
другие Boids находятся поблизости. Ключевым моментом в индивидуальном восприятии
мира каждым Boid является его понимание того, какие другие Boids находятся достаточно
близко, чтобы о них стоило беспокоиться.
- **Attractor**: Boids нужен объект, вокруг которого они будут собираться в стаю, и для этой
цели к GameObject Attractor будет прикреплен этот простой скрипт. Это не даст стае
улететь в даль.
- **Spawner**: этот скрипт будет прикреплен к Main Camera. Spawner хранит поля
(переменные), общие для всех Boids, и создает все экземпляры префаба Boid.
- **LookAtAttractor**: также прикрепленный к Main Camera, этот скрипт заставляет камеру
поворачиваться и смотреть на Attractor в каждом кадре.  

Конечно, мы могли бы сделать это с помощью меньшего количества скриптов, но каждый из них
был бы гораздо больше, чем необходимо. Этот пример следует расширению объектно-
ориентированного программирования, известному как компонентно-ориентированное
проектирование. См. боковую панель для получения дополнительной информации.

### Компонентно-ориентированное проектирование [!toc]
Паттерн «Компонент» был формализован в книге «Design Patterns: Elements» (1994)
«Группы четырёх» (Gang of Four). Основная идея
паттерна «Компонент» заключается в группировке тесно связанных функций и данных в один класс,
при этом сохраняя каждый класс максимально небольшим и сфокусированным.  

Как вы, возможно, догадались из названия, вы работали с компонентами
всё время, пока использовали Unity. Каждый GameObject в Unity - это очень небольшой
класс, который может выступать в качестве контейнера для нескольких компонентов, каждый из которых выполняет определённую - и
изолированную - задачу. Например:
- Transform отвечает за положение, вращение, масштабирование и иерархию.
- Rigidbody отвечает за движение и физику GameObject, но не за их столкновения.
- Colliders отвечают за фактическое столкновение и форму области столкновения.  

Хотя каждый из них связан с другими, они достаточно обособлены, чтобы каждый из них заслуживал отдельного компонента. Создание отдельного компонента также упрощает расширение в будущем: разделение коллайдеров от Rigidbody означает, что мы могли бы легко добавить новый тип коллайдера - например, ConeCollider или EllipsoidCollider - и Rigidbody вообще не нужно было бы изменять, чтобы учесть новый тип коллайдера.  

Это, безусловно, важно для разработчиков игровых движков, но что это значит для нас,
как для гейм-дизайнеров и создателей прототипов? Самое важное преимущество мышления в
компонентно-ориентированном ключе - это меньшие по размеру, более короткие классы. Когда ваши скрипты короче,
их легче писать, делиться ими с другими людьми, повторно использовать и отлаживать; и все это - очень благородные цели.  

Единственный реальный недостаток компонентно-ориентированного проектирования заключается в том, что его качественная реализация требует значительной предварительной подготовки, что несколько противоречит нашей философии прототипирования, которая заключается в том, чтобы всё заработало как можно быстрее. В результате этой дилеммы в третьей части этой книги вы встретите как более традиционный стиль прототипирования, когда в первых нескольких главах просто пишутся работающие фрагменты кода, так и гораздо более целенаправленный компонентно-ориентированный подход в главах, посвященных прототипу Dungeon Delver.  

Важно также понимать, что компоненты, о которых мы говорим в компонентно-ориентированном проектировании,
похожи на компоненты Unity (например, Transform, Rigidbody и т. д.),
но сильно отличаются от компонентов в системах компонентов сущностей (ECS),
описанных в конце главы «Проектирование, ориентированное на данные». Все три имеют одно и то же
название, потому что все они произошли от одной и той же базовой концепции разделения элементов кода,
но компоненты в ECS значительно меньше по размеру и не содержат никакой
функциональности.  

Для получения дополнительной информации о различных шаблонах проектирования программного обеспечения, пожалуйста, ознакомьтесь с разделом «Шаблоны проектирования программного обеспечения» в Приложении B, «Полезные концепции», а также с превосходной онлайн-книгой «Шаблоны игрового программирования» Роберта Нистрома.
</Callout>

**Скрипт Attractor**  

Скрипт Attractor управляет движением GameObject Attractor, который будет удерживать его
относительно близко к началу координат, но при этом достаточно подвижным, чтобы направлять
стаю (по извилистой круговой траектории, основанной на трех смещенных синусоидах).  

1. Выберите «Attractor» и в нижней части инспектора (возможно, вам придется прокрутить
вниз) нажмите кнопку «Add Component»:
    - a. Выберите «New Script» в нижней части появившегося всплывающего меню.
    - b. Укажите имя нового скрипта - Attractor - в поле Name (Имя) всплывающего окна.
    - c. Нажмите кнопку «Create and Add».  

Это способ одновременно создать скрипт и добавить его к GameObject за один шаг. Вы заметите,
что новый скрипт Attractor теперь находится на панели Project и был добавлен в качестве
компонента к GameObject Attractor.  

2. Откройте скрипт Attractor в Visual Studio и введите код из листинга:  

*Листинг кода Attractor.cs*

```c#
using System.Collections;
using System.Collections.Generic;
using UnityEngine;

public class Attractor : MonoBehaviour {
    static public Vector3 POS = Vector3.zero; // a

    [Header( "Inscribed" )] // b
    public Vector3 range = new Vector3( 40, 10, 40 ); // c
    public Vector3 phase = new Vector3( 0.5f, 0.4f, 0.1f ); // d


    // FixedUpdate is called once per physics update (i.e., 50x/second)
    void FixedUpdate() { // e
        Vector3 tPos = transform.position;
        tPos.x = Mathf.Sin( phase.x * Time.time ) * range.x; // f
        tPos.y = Mathf.Sin( phase.y * Time.time ) * range.y;
        tPos.z = Mathf.Sin( phase.z * Time.time ) * range.z;
        transform.position = tPos;
        POS = tPos;
    }

    // void Start() {…} // Please delete the unused Start and Update methods.
    // void Update() {…}
}
```

- a. Как `static` переменная, `POS` (сокращение от position - «положение»)
используется совместно всеми экземплярами класса Attractor (хотя в данном случае будет
существовать только один экземпляр Attractor). Это означает, что пока и POS, и класс
Attractor являются общедоступными, любой экземпляр любого другого класса может
получить доступ к POS через Attractor.POS. Это будет использоваться всеми
экземплярами Boid для удобного доступа к положению Attractor.
- b. Возможно, вы впервые видите атрибут компилятора Header. См. панель
«Заголовки в инспекторе».
- c. Поле `range` определяет максимальное расстояние, на которое Attractor сможет
удалиться от начала координат ( P:[ 0, 0, 0 ] ). При значениях по умолчанию он
никогда не будет смещаться влево по оси X дальше, чем на –40, или вправо дальше,
чем на 40.
- d. Три значения фазы будут использоваться для настройки частоты синусоидальных
волн, используемых в `FixedUpdate()`. При этих значениях частота в направлении Z
будет равна 1/5 от частоты в направлении X.
- e. `FixedUpdate()` похож на `Update()`, но вызывается один раз за физический кадр, а
не один раз за визуальный кадр. Дополнительную информацию см. в боковом блоке
«Fixed Updates и физический движок».
- f. Как упоминалось в предыдущей главе, синусоидальные волны часто используются для
циклического движения. Здесь различные значения фазы Vector3 заставляют аттрактор
перемещаться по сцене, причем каждая ось (X, Y и Z) немного сбивается с фазы по
отношению к остальным.

### Заголовки в инспекторе (Headers) [!toc]
В листинге кода приведен пример атрибута компилятора Header. Атрибуты
компилятора дают компилятору в Unity (и Visual Studio) конкретные команды и всегда
заключаются в скобки (например, `[Header( «Inscribed» )]` ). Атрибут Header
сообщает Unity, что вы хотите, чтобы над следующим публичным полем в инспекторе
отображался заглавный заголовок, выделенный жирным шрифтом. На рисунке
показаны два примера:

<img src="/images/ex29.jpeg" alt="1" style={{  height: 'auto' }} />

Атрибут компилятора Header в C# и его отображение в Инспекторе Вот два
наиболее распространённых заголовка, которые я использую в остальной части этой
книги:
- Inscribed: Я использую заголовок Inscribed, чтобы обозначить, что эти поля
предназначены для изменения в Инспекторе в качестве настроек компонента перед
нажатием кнопки «Play».
- Dynamic: Напротив, поля под заголовком Dynamic предназначены для того, чтобы
помочь вам увидеть текущее состояние скрипта в каждом кадре, и часто
перезаписываются кодом в каждом кадре. Начальные значения этих полей Dynamic
(т. е. значения, помещенные в них перед нажатием Play) почти никогда не имеют
значения, поскольку код обрабатывает эти поля как выходы, а не входы.
</Callout>

3. Сохраните скрипт, вернитесь в Unity и нажмите «Play». Вы должны увидеть, как «Attractor»

значениями диапазона, чтобы оставаться в поле зрения «Main Camera», отображаемом на
панели «Game».

### Фиксированные обновления и физический движок [!toc]
Поскольку Unity стремится работать как можно быстрее, он отображает новый кадр при
каждой возможности. Это означает, что интервал Time.deltaTime между вызовами
`Update()` может варьироваться от менее 1/1000 секунды на быстром компьютере до 1
секунды и более на очень медленном устройстве. Кроме того, частота вызовов `Update()`
резко меняется от одного кадра к другому на одном и том же компьютере в зависимости
от ряда факторов, поэтому значение Time.deltaTime между каждым вызовом
`Update()` всегда различается.  

Физические движки - такие как движок NVIDIA PhysX, традиционно используемый
Unity - полагаются на предсказуемость и стабильность, чего Update() не может
обеспечить. В результате в Unity есть обновление физики, которое всегда работает с
одинаковой частотой, независимо от того, на каком компьютере оно запущено. Частота
вызова `FixedUpdate()` задается через статическое поле `Time.fixedDeltaTime`. По
умолчанию значение `Time.fixedDeltaTime` равно `0.02f` (т. е. 1/50), что означает,
что функция `FixedUpdate()` будет вызываться 50 раз в секунду, и движок PhysX
будет обновляться.  

В результате `FixedUpdate()` лучше всего использовать для задач, связанных с чем-
либо, движущимся благодаря Rigidbody (именно поэтому мы используем его как для
обновлений Attractor, так и для Boid), а также он полезен для тех вещей, которые должны
оставаться неизменными независимо от того, на каком компьютере они работают.  

`FixedUpdate()` вызывается непосредственно перед обновлением движка PhysX. Также
имейте в виду, что - как показано на рисунке - методы ввода `GetKeyDown()`,
`GetKeyUp()`, `GetButtonDown()` и `GetButtonUp()` никогда не должны
вызываться в рамках `FixedUpdate()`, поскольку они возвращают true только
при единственном вызове `Update()` сразу после того, как произошло событие.  

На рисунке функция `FixedUpdate()` дает неверные результаты в двух точках:

<img src="/images/ex30.jpeg" alt="1" style={{  height: 'auto' }} />

Значения `true` (T) и `false` (F) методов `Input.GetKeyDown()` и
`Input.GetKeyUp()` являются достоверными в `Update()`, но недостоверными в
`FixedUpdate()`.  

>Обратите внимание, что в реальных вызовах Unity Input в качестве аргумента используется KeyCode (а не строка,
например «A»). Например, Input.GetKeyDown(KeyCode.A). Я использовал здесь «A», чтобы сэкономить место на
рисунке 27.9. Вы можете прочитать об Input в документации Unity по адресу
https://docs.unity3d.com/2020.3/Documentation/ScriptReference/Input.html — доступ 19 августа 2021 г.  

- a. Когда игрок нажимает A, GetKeyDown(«A») возвращает true только в одном вызове
Update() после нажатия клавиши, а к моменту вызова `FixedUpdate()` `GetKeyDown(«A»)` возвращает `false`.
- b. Когда игрок отпускает A, `FixedUpdate()` вызывается дважды до вызова
вызова `Update()`, поэтому `GetKeyUp("A")` возвращает `true` в обоих вызовах
`FixedUpdate()`.  

Код, вызывающий `GetKeyDown()` или `GetKeyUp()` в `FixedUpdate()`, создаст у
игрока ощущение, будто клавиатура сломана, поскольку нажатия клавиш будут
срабатывать лишь иногда.  

Даже если сейчас это не совсем понятно, просто запомните: никогда не используйте
`Input.GetKeyDown()` или любой другой метод Input, заканчивающийся на `…Down()`
или `…Up()`, внутри `FixedUpdate()`. Другие методы Input, такие как `GetKey()`
(который возвращает true все время, пока клавиша удерживается), `GetAxis()` и
`GetButton()`, работают нормально как внутри `FixedUpdate()`, так и внутри
`Update()`. Вы будете использовать подобные методы Input на протяжении всей практической части.  

>Input.GetKey() возвращает true все время, пока клавиша нажата, точно так же, как Input.GetButton()
возвращает true все время, пока кнопка нажата. Input.GetAxis() возвращает информацию о вводе как с
контроллеров, так и с клавиатуры (вы увидите это в главе 31, «Космический SHMUP — Часть 1»). Более подробную
информацию можно найти в документации Unity по адресу
https://docs.unity3d.com/2020.3/Documentation/ScriptReference/Input.html — доступ 19 августа 2021 г.
</Callout>

**Скрипт LookAtAttractor**  

Далее вам нужно заставить главную камеру следовать за движениями аттрактора.  

1. Выберите Main Camera в иерархии.
2. Создайте скрипт на C# с именем LookAtAttractor и прикрепите его к главной камере
(используя любой из методов, с которыми вы уже знакомы).
3. Откройте скрипт LookAtAttractor в Visual Studio и введите код из листинга.  

Листинг кода LookAtAttractor.cs  

```c#
using System.Collections;
using System.Collections.Generic;
using UnityEngine;

public class LookAtAttractor : MonoBehaviour {
    // void Start() {…} // Please delete the unused Start() method

    void Update() {
        transform.LookAt( Attractor.POS ); // Yep, just add this one line!
    }
}
```

4. Сохраните скрипт, вернитесь в Unity и нажмите «Play».  

Теперь главная камера будет постоянно смотреть на Attractor. Точнее говоря, вызов
transform.LookAt( Attractor.POS ) заставляет положительную ось Z трансформации
главной камеры указывать в направлении Attractor.POS.

### Скрипт Spawner — Часть 1

Скрипт Spawner будет прикреплен к Main Camera, и, следовательно, вы сможете редактировать
общедоступные поля Spawner в инспекторе Unity. Это даст вам единое место для настройки всех
параметров, влияющих на движение Boids.  

1. Выберите *Main Camera* в иерархии.
2. Используйте любой из методов, с которыми вы уже знакомы, чтобы создать скрипт на C# с
именем *Spawner* и прикрепить его к Main Camera.
3. Откройте скрипт Spawner в Visual Studio и введите код из примера (Обратите внимание,
что в примере на нескольких связанных строках присутствует комментарий // e note.)  

Листинг кода Spawner.cs

```c#
using System.Collections;
using System.Collections.Generic;
using UnityEngine;

[System.Serializable]
public class BoidSettings { // a
    // These fields allow you to adjust the flocking behavior of the Boids
    public int velocity = 32;
    public int neighborDist = 10;
    public int nearDist = 4;
    public int attractPushDist = 5;

    [Header("These \"influences\" are floats, usually from [0…4]")] // b
    public float velMatching = 1.5f;
    public float flockCentering = 1f;
    public float nearAvoid = 2f;
    public float attractPull = 1f;
    public float attractPush = 20f; // Very strong to spread out the Boids

    [Header("This determines how quickly Boids can turn and is [0…1]")]
    public float velocityEasing = 0.03f;
}

public class Spawner : MonoBehaviour {
    // SETTINGS and BOIDS are both static to allow easy access
    static public BoidSettings SETTINGS; // c
    static public List<Boid> BOIDS; // d

    // These fields allow you to adjust the spawning behavior of the Boids
    [Header("Inscribed: Settings for Spawning Boids")]
    public GameObject boidPrefab; // e
    public Transform boidAnchor; // e
    public int numBoids = 100;
    public float spawnRadius = 100f;
    public float spawnDelay = 0.1f;

    [Header("Inscribed: Settings for Spawning Boids")]
    public BoidSettings boidSettings; // f

    void Awake () {
    // Assign the boidSettings of this instance to the static SETTINGS
    Spawner.SETTINGS = boidSettings; // g
    // Start instantiation of the Boids
    BOIDS = new List<Boid>();
    InstantiateBoid(); // h
}

public void InstantiateBoid() {
    GameObject go = Instantiate<GameObject>(boidPrefab);
    go.transform.position = Random.insideUnitSphere * spawnRadius; // i
    Boid b = go.GetComponent<Boid>();
    b.transform.SetParent(boidAnchor); // j

    BOIDS.Add( b );
    if (BOIDS.Count < numBoids) {
        Invoke( "InstantiateBoid", spawnDelay ); // k
    }
  }
}
```

- a. Здесь я создал отдельный класс BoidSettings, который будет определять
поведение каждого Boid. Следует обратить внимание на несколько моментов,
касающихся этого класса:
    - Класс BoidSettings не расширяет MonoBehaviour, поэтому его нельзя прикрепить
в качестве компонента к GameObject. Это также означает, что он может находиться в
одном файле скрипта (Spawner.cs) с другими классами (ограничение Unity заключается в
том, что в одном файле .cs может существовать только один класс, расширяющий
MonoBehaviour).
    - BoidSettings имеет атрибут [System.Serializable]. Когда вы делаете класс
сериализуемым, это позволяет просматривать и редактировать класс в инспекторе Unity

    >Точнее говоря, это позволяет отображать в инспекторе любое поле, которое инспектор может сериализовать.
Сериализация — это процесс преобразования исходных данных поля в более общий текст, и он используется как
Unity Inspector, так и версией JSON (JavaScript Object Notation) от Unity, чтобы поля различных типов могли
храниться в виде обычного текста. Примером сериализации может служить преобразование красного цвета в его
шестнадцатеричную спецификацию цвета: #FF0000. Вы будете широко использовать JSON в проекте Prospector
Solitaire  

- b. Символ `\"` показывает, как ввести “ (т. е. двойную кавычку) в строковый литерал. В
инспекторе `\"` будет отображаться как “. Экранирующий символ обратная косая черта ( `\`
) позволяет вводить в строковые литералы несколько символов, в том числе: `\t`
(табуляция), `\n` (новая строка) и т. д.
- c. Поле SETTINGS является одновременно статическим (одна переменная, общая для
всех экземпляров Spawner) и общедоступным (к нему может обратиться любой класс),
что означает, что любой Boid может легко получить доступ к BoidSettings, которые
будут храниться в SETTINGS, через Spawner.SETTINGS. Поле
`Spawner.boidSettings` присваивается SETTINGS в строке // g.
- d. `static public List<Boid> BOIDS` будет содержать ссылки
на все Boids, созданные Spawner, и доступен через Spawner.BOIDS.
- e. Чтобы этот скрипт работал, необходимо задать оба поля — boidPrefab и boidAnchor
— в инспекторе Unity (в шагах 6 и 7, которые следуют далее).
- f. boidSettings — это публичный экземпляр класса BoidSettings. Поскольку
класс BoidSettings сериализуем и публичен (а все его поля также являются
`public`), вы сможете редактировать значения boidSettings в инспекторе.
- g. Здесь общедоступное поле boidSettings присваивается статическому
Spawner.SETTINGS. Это необходимо, поскольку в инспекторе Unity невозможно
задавать статические переменные. (На самом деле не обязательно предварять SETTINGS
словом Spawner., но я сделал это здесь, чтобы подчеркнуть статический характер
SETTINGS.
Поскольку BoidSettings является классом, он присваивается по ссылке, а не по типу, что
означает, что и boidSettings, и Spawner.SETTINGS указывают на один и тот же
экземпляр класса BoidSettings в памяти, поэтому любые изменения, внесенные в
boidSettings в компоненте «Настройки» инспектора главной камеры, также
применяются к Spawner.SETTINGS.
- h. InstantiateBoid() изначально вызывается один раз функцией Awake(), а затем
InstantiateBoid() использует функцию Invoke() (в строке // k), чтобы
вызывать себя снова, пока количество созданных Boids не станет равным numBoids.
- i. Эта строка устанавливает положение нового Boid в любом месте в пределах
spawnRadius единиц от начала координат (т. е. в пределах 100 единиц от [ 0, 0, 0 ]).
Статическое свойство insideUnitSphere класса Random является свойством только
для чтения, которое генерирует случайный Vector3, расположенный где-то внутри сферы с
радиусом 1 единицы. Затем мы умножаем это на spawnRadius, чтобы присвоить
данному экземпляру Boid случайное положение где-то на расстоянии spawnRadius от
начала координат (позиция [ 0, 0, 0 ]).
- j. Сделав всех Boids дочерними элементами одного и того же Transform GameObject,
можно сохранить порядок в панели «Иерархия». Эта строка помещает их всех под один
родительский Transform boidAnchor (Transform GameObject BoidAnchor в иерархии).
Если вы хотите увидеть всех Boids, перечисленных в иерархии, вам просто нужно
щелкнуть треугольник раскрытия рядом с GameObject BoidAnchor, который является их
родителем.
- k. Два аргумента, которые принимает Invoke, — это имя вызываемого метода (в виде
строки: «InstantiateBoid») и время ожидания перед его вызовом (spawnDelay,
или 0,1 секунды).  

4. Сохраните скрипт Spawner и вернитесь в Unity.
5. Выберите «Main Camera» в панели «Hierarchy», и в инспекторе появятся общедоступные
поля компонента «Spawner», в том числе треугольник раскрытия, с помощью которого
можно просматривать и редактировать значения boidSettings (в нижней части
компонента «Spawner (Script)»).
6. Присвойте префаб Boid из панели «Проект» полю boidPrefab в инспекторе
компонента Main Camera Spawner (Script).
7. Назначьте GameObject BoidAnchor из панели «Иерархия» полю boidAnchor
в инспекторе компонента Main Camera Spawner (Script).  

Попробуйте нажать Play в Unity. Вы увидите, что Spawner создает новый экземпляр Boid в
качестве дочернего объекта BoidAnchor каждые десять сотых секунды в течение десяти секунд,
и Boids распределяются в пределах сферы радиусом 100 м, но пока ничего не делают. Вернёмся
к скрипту Boid.  

### Скрипт Boid — Часть 2

Выполните следующие шаги, чтобы инициализировать цвет и движение Boid:  

1. Откройте скрипт Boid в Visual Studio и введите код:  

**Листинг кода Boid.cs**

```c#
using System.Collections;
using System.Collections.Generic;
using UnityEngine;

public class Boid : MonoBehaviour {

    private Rigidbody rigid; // a

    // Use this for initialization
    void Awake () {
        rigid = GetComponent<Rigidbody>(); // a

        // Set a random initial velocity
        vel = Random.onUnitSphere * Spawner.SETTINGS.velocity; // b

        LookAhead(); // c
        Colorize(); // d
    }

    // Orients the Boid to look at the direction it’s flying
    void LookAhead() { // c
        transform.LookAt(pos + rigid.velocity);
    }

    // Give the Boid a random color, but make sure it’s not too dark
    void Colorize() { // d
        // Choose a random color
        Color randColor = Random.ColorHSV( 0, 1, 0.5f, 1, 0.5f, 1 ); // e

        // Assign the color to the Renderers of both the Fuselage and Wing
        Renderer[] rends = gameObject.GetComponentsInChildren<Renderer>(); // f
        foreach ( Renderer r in rends ) {
            r.material.color = randColor;
        }

        // Also assign the color to the TrailRenderer
        TrailRenderer trend = GetComponent<TrailRenderer>(); // g

        trend.startColor = randColor;
        randColor.a = 0;
        trend.endColor = randColor;
        trend.endWidth = 0;
    }

    // Property used to easily get and set the position of this Boid
    public Vector3 pos { // h
        get { return transform.position; }
        private set { transform.position = value; }
    }

    // Property used to easily get and set the velocity of this Boid
    public Vector3 vel { // h
        get { return rigid.velocity; }
        private set { rigid.velocity = value; }
    }
}

```
