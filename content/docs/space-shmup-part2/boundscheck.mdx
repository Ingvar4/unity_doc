---
title: В каких случаях приватность BoundsCheck (bndCheck) становится проблемой?
description: Сначала я объясню, почему тот факт, что поле `bndCheck` является закрытым (`private`), может стать проблемой.
---

В классе `Enemy` поле `bndCheck` объявлено как `private`, а это означает, что оно доступно только членам класса `Enemy`.

```c#
private BoundsCheck bndCheck;
```

Это означает, что поле доступно внутри класса Enemy, но не в других классах, включая
Enemy_1, несмотря на то что Enemy_1 является подклассом Enemy. Иными словами,
методы `Awake()` и `Move()` класса Enemy могут обращаться к bndCheck и взаимодействовать
с ним, тогда как переопределенный метод `Move()` в классе Enemy_1 «не знает» о существовании
поля bndCheck. Чтобы проверить это:  

1. Откройте скрипт Enemy_1 и раскомментируйте строку `print()`, в конце метода `Move()`.  
    Листинг кода Enemy_1.cs

```c#
public class Enemy_1 : Enemy {
    …

    public override void Move() {
        …
        // base.Move() still handles the movement down in y
        base.Move();

        print( bndCheck.isOnScreen ); // <== Uncomment this line!
    }
}
```

Поскольку переменная bndCheck является закрытой (private) в классе Enemy, класс Enemy_1 не может получить к ней доступ (то есть читать или изменять её); (в Visual Studio она подчеркивается красной линией и вызывает ошибку компиляции, которая отображается в консоли Unity как ошибка, выделенная красным). Чтобы исправить это, нужно изменить модификатор доступа переменной bndCheck с public на protected. Как и закрытые (private) переменные, защищенные (protected) переменные недоступны для большинства других классов, однако, в отличие от закрытых, они видны подклассам и могут ими наследоваться. Следует отметить, что закрытые переменные класса доступны всем членам этого класса.

Примечание: я выделил слова «Да» в приведенной выше таблице жирным шрифтом и красным цветом, поскольку, как правило,
предоставление доступа к чему-либо большему числу объектов сопряжено с риском.  

2. Откройте скрипт Enemy и измените модификатор доступа поля bndCheck с private на protected.  
    Листинг кода Enemy.cs

```c#
public class Enemy : MonoBehaviour {
    …
    public int score = 100; // Points earned for destroying this

    protected BoundsCheck bndCheck; // Change bndCheck from private to protected

    void Awake() { … }
    …
}
```

Сохраните все скрипты в Visual Studio. Теперь, если вы посмотрите на скрипт Enemy_1 в Visual Studio,
bndCheck.isOnScreen больше не будет подчеркнут красным, и код успешно скомпилируется,
а ошибка в консоли исчезнет.  

>Если ошибка не исчезает из окна Console, нажмите на треугольник рядом с кнопкой Clear в этом окне
и убедитесь, что установлены флажки Clear on Play и Clear on Build. В противном случае старые ошибки останутся в списке,
и вы можете не заметить, что уже исправили их.  

3. Вернитесь в Unity и нажмите кнопку Play. Теперь вы должны увидеть, что объекты Enemy_1 выводят в лог множество сообщений о своем появлении на экране или исчезновении с него.
4. Вернитесь к скрипту Enemy_1 в Visual Studio и снова закомментируйте строку с командой `print()`, чтобы прекратить вывод этих сообщений.  
    Листинг кода Enemy_1.cs

```c#
public class Enemy_1 : Enemy {


public override void Move() {
        …
        // base.Move() still handles the movement down in y
        base.Move();

        // print( bndCheck.isOnScreen ); // <== Finally, comment out this line!
    }
}
```

5. Сохраните скрипт Enemy_1.

Но тогда почему `private bndCheck` не создавало проблем для `Enemy_0`?  

Заранее прошу прощения за то, что этот момент может показаться довольно специфическим, но он важен.  

Возможно, вы задаетесь вопросом: если поле `bndCheck` было объявлено как `private` (закрытое), почему метод `Awake()`, который класс `Enemy_0` наследует от `Enemy`, все равно мог его видеть?  

Суть вот в чем: хотя `Awake()` и наследуется классом `Enemy_0`, этот метод остается частью суперкласса `Enemy`. Поэтому он сохраняет доступ к закрытым полям (и другим закрытым элементам) класса `Enemy` даже тогда, когда вызывается в контексте класса `Enemy_0`.  

Таким образом, методы `Awake()` и `Update()`, определенные в классе `Enemy`, «видят» `bndCheck`, в то время как любые методы, написанные внутри `Enemy_0`, доступа к нему не имеют (как мы уже видели на примере `Enemy_1`). Конечно, теперь `bndCheck` имеет модификатор `protected` (защищенный), поэтому он доступен любым подклассам `Enemy` (включая `Enemy_0` и `Enemy_1`), но описанный выше нюанс — важный аспект наследования классов, о котором вам стоит знать.
Чтобы освежить знания о классах и наследовании (в том числе о переопределении методов), обратитесь к главе «Классы».
