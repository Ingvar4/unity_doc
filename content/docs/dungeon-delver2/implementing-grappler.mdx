Теперь вы можете увидеть, как этот предмет мог бы работать, если
бы он был частью первой игры Zelda. В Dungeon Delver Grappler представляет собой крюк, который
Дрей может выстреливать и прикреплять к стенам, после чего он притягивает Дрея к стене, в том
числе перетягивая его через ранее непроходимые красные плитки. У Grappler также есть две
дополнительные способности: он может наносить небольшой урон врагам и притягивать PickUps к
Дрею.  

Честно говоря, реализация Grappler стала одной из самых сложных задач при подготовке третьего
издания книги. Во втором издании Grappler был реализован с помощью некой «хакерской» уловки,
которая включала код, перехватывающий управление движением Dray путем установки значения
поля enabled в скрипте Dray равным false. Как упоминалось в совете ранее в этой главе, всякий
раз, когда поле enabled MonoBehaviour устанавливается в false, он больше не получает ни
одного из следующих сообщений: Start(), Update(), FixedUpdate(), LateUpdate(),
OnGUI(), OnDisable() и OnEnable(). С тех пор я пришел к выводу, что это был неэлегантный
способ для снятия управления с Dray. Кроме того, поскольку enabled является публичным полем, у
человека, не знакомого с кодом, не было бы возможности добавить точку останова отладчика и увидеть,
какой код меняет значение enabled с true на false.  

В этой третьей версии я хотел сделать лучше. При переработке этого кода я учитывал несколько
моментов:
    - Код должен быть расширяемым на случай, если вы захотите добавить в игру другие гаджеты
(например, бумеранг, лук, фонарь). Это будет реализовано с помощью интерфейса IGadget.
    - Когда Grappler берет на себя управление движением Dray, эта возможность должна быть
хотя бы в некоторой степени отлаживаемой из скрипта Dray.
    - Код Grappler должен быть максимально читабельным и лаконичным.
Мне потребовалось несколько недель, чтобы довести код Grappler до состояния, которое меня
устраивало, и на следующих страницах я постараюсь изложить некоторые из моих соображений.

### Интерфейс IGadget [!toc]
В оригинальной игре The Legend of Zelda для NES было несколько гаджетов, которые Линк мог
использовать после их получения. Хотя мы будем реализовывать только один гаджет - Grappler, все
же стоит структурировать код так, чтобы в будущем можно было добавлять и другие гаджеты.
Обычно я не делаю этого в первом прототипе игры, но именно об этом я начинаю думать, когда
перехожу от прототипа к фактическому производству игры.  

Интерфейс IGadget должен работать с любым гаджетом, который может быть создан для Dray.
Конечно, я уверен, что вы сможете придумать всевозможные гаджеты, о которых я даже не подумал, но
этот интерфейс IGadget будет работать с любыми гаджетами из оригинальной игры для NES. Чтобы
создать интерфейс IGadget:  

1. Создайте новый скрипт с именем IGadget в папке « » в папке «Scripts».
2. Откройте скрипт IGadget в Visual Studio и удалите все, что в нем находится.
3. Введите код из листинга в скрипт IGadget. Это весь скрипт. Поскольку IGadget не
использует никаких классов, специфичных для Unity, нам даже не нужно использовать
UnityEngine; в начале.  
          Листинг кода IGadget.cs
```c#
public interface IGadget { // a
    bool GadgetUse(Dray tDray, System.Func<IGadget, bool> tDoneCallback); // b
    bool GadgetCancel(); // c
    string name {get;} // d
}
```

    - a. Убедитесь, что вы объявляете IGadget как интерфейс, а не как класс.
    - b. GadgetUse() будет вызываться всякий раз, когда игрок нажмет клавишу гаджета (по
умолчанию - X на клавиатуре). Передается экземпляр Dray tDray, чтобы любой IGadget
мог получить доступ к необходимой информации из Dray. Второй, более сложный параметр
tDoneCallback - это делегат для функции обратного вызова, которую IGadget будет вызывать, когда
закончит работу (подробнее об этом вскоре!). GadgetUse() возвращает true, если
IGadget готов и может использоваться, или false, если что-то пошло не так (например,
если Grappler не готов к стрельбе).  

Эти параметры имеют префикс t, чтобы обозначить их как временные параметры, переданные
в метод. Это связано с тем, что я ожидаю, что имена полей внутри классов, реализующих
IGadget, будут похожими (например, Dray tDray будет присвоен полю Dray dray в
коде Grappler из листинга).
    - c. GadgetCancel() вызывается всякий раз, когда использование гаджета прерывается;
например, когда Enemy сталкивается с Dray во время использования гаджета. Как и
GadgetUse(), GadgetCancel() возвращает true, если IGadget успешно
отменяется, или false, если что-то пошло не так.
    - d. name будет использоваться для того, чтобы сообщения Debug.Log() могли
отображать имя GameObject, к которому прикреплен IGadget.  

#### `The System.Func<T,TResult> Delegate` [!toc]
`System.Func<T,TResult>` - это особый вид делегата, который может принимать любую
функцию с одним входным параметром типа T и выходом типа TResult. Например, делегат
`System.Func<IGadget,bool> tDoneCallback` в строке `// b` листинга кода - это
делегат, к которому можно привязать любую функцию, если эта функция имеет IGadget в
качестве типа входа и возвращает bool.  

Как и любой другой делегат, `System.Func<T,TResult>` может быть многократно присвоен (т. е.
к нему можно присвоить несколько функций с помощью оператора +=). Преимущество общих
параметров (T и TResult) заключается в том, что мы можем создать делегат Func (например,
tDoneCallback) без необходимости заранее отдельно определять тип делегата. Без использования
`System.Func<T,TResult>` нам пришлось бы объявить конкретный тип делегата, который мог
бы принимать в качестве входных данных только IGadget и возвращать только bool, но
определения таких вещей, как типы делегатов, не могут выполняться внутри определения
интерфейса, такого как IGadget.  

>Существует также общий тип делегата `System.Action<T>`, который можно использовать для функций с типом возвращаемого значения void. Существуют также версии Action и Func, которые могут принимать до 16 аргументов. Довольно краткое обсуждение этих общих типов делегатов можно найти по адресу https://social.technet.microsoft.com/wiki/contents/articles/22418.c-action-func-tresult-and-predicate-t-delegate.aspx  

Теперь, когда IGadget определён - и мы немного поговорили о делегатах Func - мы можем
изменить класс Dray, чтобы использовать любой гаджет.  

### Понимание того, как Dray работает с IGadgets [!toc]
Поведение Dray при использовании гаджета будет похоже на то, как они атакуют своим мечом:  

1. Игрок нажимает кнопку использования гаджета (X на клавиатуре).
2. Dray вызывает GadgetUse() на IGadget и передает метод обратного вызова, который мы
назовем GadgetIsDone(). Если GadgetUse() возвращает false, то Dray возвращается в
режим eMode.idle.
3. Если GadgetUse() возвращает true, то Дрей воспроизводит правильную анимацию атаки
для своего направления с анимационной скоростью 0 (т. е. анимация атаки застывает на первом
кадре) и переключается в режим eMode.gadget.
4. Dray ожидает в режиме eMode.gadget, ничего не делая, пока GadgetIsDone() не будет
вызван IGadget; однако, если что-либо поразит Dray и нанесет урон, Dray вызовет
GadgetCancel() на IGadget, а затем отреагирует на удар.
5. Если не произойдет никакого прерывания, вызывающего вызов GadgetCancel(),
то IGadget вызовет GadgetIsDone(), когда захочет, чтобы Dray вышел из
режима eMode.gadget.  

Если бы Дрей стрелял из лука или бросал бумеранг, то GadgetIsDone() вызывалась бы уже через
0,5 секунды, чтобы Дрей мог продолжать передвигаться, пока летит стрела или бумеранг. Но с
Grappler Дрей будет оставаться в режиме eMode.gadget до тех пор, пока либо Grappler не вернется
к Дрею, либо Дрей не будет притянут к Grappler, либо Дрей не получит урон от чего-либо (что может
произойти в любой момент, кроме того, когда Дрей притягивается к Grappler). Одно из действительно
классных свойств того, как мы это реализуем, заключается в том, что способ взаимодействия класса
Dray с IGadget одинаков независимо от того, какой именно это гаджет.  

### Включение поддержки IGadgets в Dray [!toc]
Мы добавим несколько фрагментов кода в Dray, чтобы включить использование IGadgets.  

1. Откройте скрипт Dray в Visual Studio и внесите изменения. В этом скрипте много изменений, поэтому будьте внимательны, чтобы ничего не пропустить.  
          Листинг кода Dray.cs
```c#

    /// Matches the System.Func<IGadget, bool> delegate type required by the
```

    - b. Поскольку в этом коде мы добавляем ключ use gadget, давайте также сделаем его более
гибким, чтобы вы могли выбирать нужные ключи как для атаки, так и для гаджета в
инспекторе Unity.
    - c. startWithGrappler будет использоваться позже (в строке // c листинга кода 36.30),
чтобы позволить Дрею начинать с Grappler, а не подбирать его.
    - d. keyGadget (по умолчанию X на клавиатуре) - это кнопка использования гаджета. Нажатие
на нее вызывает GadgetUse() на currentGadget (передавая метод GadgetIsDone для
использования в качестве обратного вызова), и если вызов GadgetUse() возвращает true,
то Dray переводится в режим eMode.gadget, а его скорость устанавливается на 0.
Размещение этого кода после кода, который меняет режим на основе dirHeld, и перед
кодом, который меняет режим при нажатии keyAttack, означает, что атака будет иметь
приоритет над использованием гаджета, а использование гаджета - над движением.
    - e. Здесь метод GadgetIsDone передается в вызов currentGadget.GadgetUse() в
качестве параметра (где он будет добавлен в делегат gadgetDone-Callback экземпляра
Grappler; см. строку // c в листинге кода 36.29). Обратите внимание: когда метод
передается в вызов функции таким образом, он должен передаваться без скобок после него.
(Если бы скобки были, то вызывался бы метод GadgetIsDone(), и результат (в данном
случае, возвращаемое значение типа bool из GadgetIsDone() в строке // l) передавался
бы в GadgetUse() вместо самого метода GadgetIsDone).
    - f. Обязательно измените KeyCode.Z здесь на keyAttack.
    - g. Если mode == eMode.gadget, анимация атаки воспроизводится со скоростью 0 в
правильном направлении, позиционируя GameObject Dray с вытянутой рукой, как будто он
атакует или бросает гаджет.
    - h. Эти три строки перемещаются в оператор if в `// i`. Удалять их не нужно, но необходимо
заключить их в оператор if в // i.
    - i. Если игрок получает удар от врага (то есть когда вызывается OnCollisionEnter2D()), и
он не находится в режиме eMode.gadget, выполняются три строки, перемещенные сюда из
// h. См. боковую панель «Сокращенные операторы и вызовы функций» для получения
дополнительной информации о части currentGadget.GadgetCancel() этой строки.
    - j. Это первый случай использования директивы компилятора #region в данной книге.
Директивы #region просто определяют участок кода как имеющий конкретное назначение.
Здесь мы используем её, чтобы выделить код в Dray, который имеет отношение к IGadgets.
Конечно, часть кода IGadget разбросана по остальной части скрипта Dray.cs, но размещение
#region здесь позволит вам позже легко найти большую часть кода, связанного с IGadgets.
Все директивы компилятора #region должны сопровождаться директивой #endregion,
расположенной далее в коде.  

При желании вы также можете добавить #region IKeyMaster_Implementation и
#endregion вокруг соответствующего раздела, предшествующего этому в коде.  

Примечание: Не следует вводить `// j` в конце этой строки в Visual Studio, так как он будет
интерпретироваться как часть имени #region.  

    - k. Это автоматическое свойство currentGadget с частным условием set содержит ссылку
на выбранный в данный момент IGadget Dray, что позволяет позже добавлять в игру
дополнительные IGadgets.
    - l. GadgetIsDone() будет вызван IGadget, когда он захочет, чтобы Дрей вышел из режима
eMode.gadget. Как упоминалось ранее, гипотетический бумеранг вызвал бы эту функцию
через 0,5 секунды, чтобы позволить Дрею передвигаться, пока бумеранг летит, но Grappler
вызовет её только тогда, когда либо вернётся к Дрею, либо закончит тянуть Дрея к себе.

### Операторы сокращения и вызовы функций [!toc]
Строка на `// i` в листинге кода демонстрирует важное использование сокращающего
оператора OR:
```c#
if ( mode != eMode.gadget || currentGadget.GadgetCancel() ) { // i
```
Если выполнение кода доходит до этой строки, и Dray находится в режиме eMode.gadget,
вызывается GadgetCancel() для currentGadget (попытка отменить использование
гаджета), и если это удается, обратный вызов GadgetIsDone() установит режим в
eMode.idle. Этот вызов GadgetCancel() в первую очередь используется для отключения
гаджета (например, если по Dray ударили, когда Grappler делает что-либо, кроме притягивания
Dray к себе, это заставит Grappler вернуться в состояние покоя), но он также позволяет
IGadget предотвратить отталкивание Dray, возвращая false (хотя Dray все равно получит
урон).  

Если же, с другой стороны, Дрей не находится в режиме eMode.gadget, то
GadgetCancel() не вызывается. Это связано с сокращающим характером оператора ||.
Если первое условие (mode != eMode.gadget перед ||) истинно, то оператор ||
сокращается, и второе условие (currentGadget.GadgetCancel()) никогда не
вычисляется. Таким образом, currentGadget.GadgetCancel() вызывается только в
том случае, если Dray находится в режиме eMode.gadget.  

Теперь у Dray есть возможность использовать IGadget, но нам все еще нужно создать гаджет,
который они смогут использовать.
</Callout>
