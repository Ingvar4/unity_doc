В ходе работы над этим изданием я написал несколько примеров ECS, и
каждый из них переставал компилироваться всего через несколько месяцев
после написания, поскольку Unity ECS сильно изменилась. Однако теория
ECS стабильна, и именно ее я опишу здесь.  

Помимо реализации в Unity, ECS состоит из трех основных концепций:  

- Сущности (Entities): концептуально они похожи на GameObjects, но
фактически сущность — это просто однозначное целое число без знака,
которое группирует набор компонентов.
- Компоненты (Components): молекулярные фрагменты данных,
как правило, настолько малые, насколько это возможно для
данных типа.  

>Примером молекулярного фрагмента данных может служить, например, положение (три
числа с плавающей запятой) или кватернион (четыре числа с плавающей запятой). Под
«молекулярным» я подразумеваю, что это самый маленький фрагмент данных, который
вам понадобится одновременно.  

- Системы: функции, которые действуют на сущности, имеющие
нужный набор компонентов. Также они должны быть как можно
меньше, чтобы упростить кодирование.  

### Переход к мышлению ECS

программировании нас приучили рассматривать каждый элемент нашей игры
как объект — представленный классом — обладающий как данными, так и
функциональностью. Давайте посмотрим, как это работает в классической
игре Atari «Asteroids», разработанной Лайлом Рейнсом и Эдом Логом. На

Например, в ООП объект PlayerShip имеет положение и скорость, а

### Компоненты — это молекулы данных

В ECS объекты в игре разбиты на компоненты, которые я люблю представлять
себе как «молекулярные» фрагменты данных — они не являются наименьшими
возможными битами (т. е. не атомарны); скорее, это наименьший фрагмент,
который всегда нужно группировать. Например, 2D-позиции всегда
потребуются значения `float` для `x` и `y`, поэтому имеет смысл хранить их вместе
как `float2`. Таким образом, вы можете создать компонент `Com_Position`,
как показано в листинге кода. (Примечание: листинг кода представляет собой псевдокод, то есть он передает концепцию, но в настоящее время не должен работать в Unity C#.)  

Листинг 28.12 Псевдокод компонента Com_Position

```c#
public struct Com_Position : IComponentData {
    public float2 Value;
}
```

Как видите, он очень маленький. И каждый определяемый вами компонент
ECS должен быть очень маленьким. Подобно молекулярным данным,
компоненты представляют собой наименьшие фрагменты данных, к которым
вам всегда требуется одновременный доступ. Наш новый компонент
`Com_Position` будет использоваться всевозможными системами:
`Sys_UpdatePostion`, `Sys_ScreenWrap`, `Sys_Collide`,
`Sys_SpawnPlayerShot` и `Sys_SpawnSmallerAsteroids` — все они
будут считывать и/или записывать компоненты `Com_Position`.  

>Если вы все же хотите связать систему с конкретным типом сущности (например, чтобы
добавить ввод игрока к сущности PlayerShip), сейчас принято создавать пустой компонент
`Com_PlayerShip`, прикрепленный только к сущности PlayerShip, а затем писать систему
`Sys_PlayerInput`, которая работает только с сущностями, имеющими компонент
`Com_PlayerShip`.  

### Системы действуют на группы компонентов

В ECS системы вообще не связаны с конкретными сущностями или
типами сущностей. Вместо этого каждая система предназначена для
воздействия на любую сущность, имеющую искомые компоненты.
Например, `Sys_UpdatePosition` будет воздействовать на любую
сущность, имеющую компоненты `Com_Position` и `Com_Velocity`.

```c#
public struct Sys_UpdatePosition : ComponentSystem {
    protected override void OnUpdate() {
        Entities.ForEach(ref Com_Position pos,[ReadOnly] ref Com_Velocity vel) =>
        {
            pos.Value += vel.Value * Time.deltaTime;
        }
    }
}
```

Все системы являются подклассами `ComponentSystem` и должны
переопределять метод `OnUpdate()`, который вызывается в каждом кадре.
Код в третьей строке означает: для каждого объекта (Entity), имеющего
компоненты `Com_Position` и `Com_Velocity`, выполнить код в строке 5.
Также стоит отметить, что ссылка на компонент `Com_Velocity` помечена
как `[ReadOnly]`. Пока `Com_Velocity` будет считываться только заданиями, система заданий может запланировать параллельное выполнение
нескольких заданий, которые считывают данные из него.  

>В реальном коде Unity ECS, вероятно, пришлось бы избегать ссылки на Time.deltaTime, но
это псевдокод.  

Символ `=>`, который вы видите в конце 3-й строки, представляет собой
лямбда-выражение и используется для определения небольших безымянных
функций. В листинге кода он обеспечивает выполнение 5-й строки для
каждого объекта Entity, соответствующего критериям `ForEach()`.  

### ECS Storage минимизирует промахи кэша  

Как показано на рисунке, компоненты всех сущностей хранятся вместе
в массивах каждого типа компонента. Это значительно улучшает локальность
данных. Примерной системе `Sys_UpdatePosition` потребуется доступ
только к массивам компонентов `Com_Position` и `Com_Velocity`, и она
никогда не будет загружать в кэш-память массивы других компонентов.

### An Entity Is an Index  

Поскольку данные организованы по компонентам, лучший способ представить
себе сущность — это индекс, который указывает, какие `Com_Position`,
`Com_Velocity`, `Com_Rotation` и другие компоненты в различных
массивах относятся к одной сущности.  

Поскольку сущность — это простой индекс, используемый для поиска нужных
компонентов (в отличие от класса, который содержит ссылки на свои данные в
памяти), `Sys_UpdatePosition` никогда не запрашивает никаких данных,
кроме двух компонентов, которые ему нужны; ни один из остальных компонентов,
входящих в состав каждого объекта, никогда не извлекается из оперативной
памяти в кэш-память.

### Преимущества ECS

«Производительность по умолчанию» — это слоган Unity для DOTS, и он
вполне заслужен. Основная структура ECS гарантирует, что ваш код отлично
настроен для локальности данных, системы заданий C# и компилятора Burst,
что в совокупности максимально повышает скорость и эффективность на
современных процессорах. Кроме того, разработчики, имеющие опыт работы
с ECS, утверждают, что хотя первоначальный переход на ECS был
болезненным, после его внедрения как добавление новых функций, так и
отладка существующих стали значительно проще.  

### Будущее Unity DOTS

Хотя Unity уже несколько лет привержена DOTS, их отношение к ней,
похоже, изменилось. Изначально посыл был примерно таким: «Вы больше
никогда не будете использовать ООП!» — что было довольно пугающим для
многих людей, которые потратили годы на изучение как объектно-
ориентированного программирования, так и тонкостей написания кода для
Unity C#. В последнее время это изменилось на «Вы должны использовать
DOTS, когда это необходимо» и «Если вы с самого начала разрабатываете для
DOTS, ваш проект будет более производительным и проще в обслуживании».  

Unity также начала заменять некоторые из своих основных библиотек кода на
версии DOTS, включая систему Unity Physics (разработанную совместно с
Havok для замены старой системы NVIDIA PhysX с поддержкой « ») и новый
сетевой код. Система Unity Physics уже работает довольно хорошо и
включает в себя несколько очень интересных улучшений, таких как
возможность запуска нескольких физических симуляций одновременно и
возможность запуска прогнозирующей физики (например, показывая игроку,
куда полетят все шары на бильярде). Сетевая библиотека NetCode на базе
DOTS еще довольно далека от выпуска, хотя с ее помощью уже создано
несколько впечатляющих демо-версий.  

Как я упоминал ранее в этой главе, библиотека ECS Unity претерпела
радикальные и быстрые изменения на протяжении всего процесса разработки.
Похоже, главная причина этого заключается в том, что Unity прилагает
огромные усилия, чтобы сделать код ECS менее сложным. Таким образом,
вместо того чтобы ожидать от разработчиков создания сущностей (Entities),
компонентов (Components) и систем (Systems) с нуля, Unity создала рабочий
процесс преобразования, который позволяет разработчикам создавать
GameObjects в Unity как обычно, а затем они автоматически преобразуются в
сущности во время выполнения.  

Помимо явных преобразований, я ожидаю, что Unity продолжит переход
внутреннего кода на DOTS, предоставляя всем разработчикам некоторые
преимущества DOTS, при этом по-прежнему поддерживая более
традиционные рабочие процессы и кодирование Unity.  

Чтобы узнать больше о стратегии Unity в отношении DOTS, я рекомендую
посетить веб-сайт Unity DOTS по адресу https://unity.com/dots.  

Unity также провела отличную серию докладов по DOTS на Unite Copenhagen
2019, которые можно найти, введя запрос «Unite Copenhagen 2019 DOTS» на
YouTube.com. В частности, Майк Гейг (Mike Geig) отлично обосновывает
преимущества DOTS в своем докладе «Converting Your Game to DOTS.»
